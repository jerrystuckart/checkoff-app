# DVA-1 v2 — Legacy Operator Instruction Classification

The verbatim text in `v2.md` is never edited. This file identifies which
passages describe the OLD manual workflow (Jerry pasting a destination
name into a fresh Claude Project conversation) rather than the
destination-evaluation methodology itself. Chief's orchestration layer
(`destinationHubDriver.ts`) supersedes these specific passages while the
evaluation methodology around them stays byte-for-byte unchanged.

## Classified `legacy_operator_instruction`

1. **"How to use this project" / "Start a new conversation and enter only a destination and state..."** (lines 5–11) — describes the manual single-conversation-per-destination workflow. Superseded: Chief creates one `SpecialistExecutionRequest` per destination automatically via `driveDestinationHub()`; "fresh conversation" has no meaning in the orchestration layer.

2. **Final Statement (line 821): "DVA-1 is complete. No additional research has been performed beyond this initial screening. Awaiting Jerry's approval before beginning DVA-2."** — the "awaiting Jerry's approval" clause describes the old hand-off (Jerry manually copying the DVA-1 output into the DVA-2 Project). It is **not** presented anywhere in the substantive methodology (Sections 1–13, Agent Rules) as a founder-judgment requirement tied to the destination's own merits.

   **Substantive rule found instead (Section 13 — Current-Strategy Fit, lines 775–813):** this IS the real, substantive gate. A destination can score highly (even Elite, 90–100) yet be classified "⚠️ Strong Opportunity, But Later-Stage" — CheckOff is deliberately targeting smaller weekend destinations first. That classification, not a blanket "always ask Jerry," is what determines whether DVA-2 should wait for founder review. See `evaluateDVA1Gate()` in `destinationHubLifecycle.ts` for the exact rule Chief now applies: routine, qualified, current-strategy-fit progression advances to DVA-2 automatically; the later-stage and weak-fit cases still escalate to Jerry.
