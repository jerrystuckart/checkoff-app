# DVA-2 v2 — Chief Orchestration Wrapper

Chief-facing contract around `v2.md`. Never restates the rubric.

## Input contract

- Required prior-stage artifact: a `DVA1Artifact` for the SAME `destinationId`, referenced by `consumedDva1ArtifactRef` on the resulting `DVA2Artifact` — validated by `validateDva2Input()` (hard reject on any mismatch).

## Expected structured output (`DVA2Artifact`, `destinationHubLifecycle.ts`)

Pulled directly from the rubric's own decision sections — never re-derived:

- `worthPursuing` — Section 23: Yes / Maybe / No
- `recommendedPriority` — Section 23: `HIGH_PRIORITY_CREATE_DAP` / `VIABLE_CREATE_DAP_WHEN_CAPACITY_ALLOWS` / `PROMISING_BUT_PREMATURE_MONITOR` / `DO_NOT_PURSUE_CURRENTLY`
- `recommendedNextStep` — Section 24 (DAP Handoff): `BUILD_DAP_NOW` / `HOLD_DAP_UNTIL_ISSUE_RESOLVED` / `STOP_PURSUIT` — **this is the field the gate below actually routes on**, since it's the rubric's own explicit hand-off instruction to the next stage.
- `rationale`, `knownRisks`, `evidenceGaps` (from Section 24's "Questions DAP Must Resolve")

**Corrected from Phase 2C/2D/2F**: no `GREEN`/`YELLOW`/`RED` field exists in the source methodology — that vocabulary was an unretrieved paraphrase. See `v2.legacy-operator-instructions.md` for the full correction record.

## Gate fields / automatic advancement rule

`routeDVA2Recommendation()`:

| `recommendedNextStep` | outcome |
|---|---|
| `BUILD_DAP_NOW` | **auto-advance** to DAP — `pipelineState: READY`, no Jerry gate (same "routine qualified progression" principle as DVA-1→DVA-2; `destination_hub.draft_dap` is already `AUTO` in `standingAuthority.ts`) |
| `HOLD_DAP_UNTIL_ISSUE_RESOLVED` | `pipelineState: WAITING` — `NEEDS_JERRY` if the artifact names no further research path, otherwise research continues first |
| `STOP_PURSUIT` | `pipelineState: HOLD` (never `DECLINE` — "do not permanently discard potentially useful future destinations merely because timing is wrong today" still holds) — routine, no Jerry needed |

## Artifact identity requirement

`DVA2Artifact.destinationId` must match both the execution's own
destinationId AND `DVA1Artifact.destinationId` — enforced by
`validateDva2Input()` plus the runtime's own `assertExecutionIdentity`.
