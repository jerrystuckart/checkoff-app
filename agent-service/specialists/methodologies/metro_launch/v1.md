# Metro Launch Methodology — v1

`methodologyId: metro_launch` `version: v1` `owningSpecialist: metro_builder` (coordinates `research_verifier`, hands off to `checkoff_editor` and `business_outreach`)

This is the canonical, versioned methodology `metro_builder` executes for every stage in
`agent-service/playbooks/metroLaunch.ts` (`M0`–`M15`). It supersedes ad hoc prompting — a
specialist execution against this playbook must record `methodologyId: 'metro_launch'` and
`methodologyVersion: 'v1'` on its result envelope (Phase 2D requirement).

Every section below is tagged **[RECOVERED]** (a real, evidenced practice from a prior metro
launch — Phoenix, Tucson, Denver/Boulder/Longmont, or Milwaukee) or **[NEW]** (a Phase 2D
recommendation formalizing a gap, not something that was previously written down or consistently
done). Nothing here is invented as if it were historical fact — see the provenance note at the
end of each section.

## M0 — Metro Definition **[RECOVERED — mechanics; NEW — as a named checklist]**

Capture, before any research starts:
metro name, slug, included cities/suburbs, explicitly excluded areas, IANA timezone, launch
season (nullable — a real, deferred decision is fine), target catalog range.

**[RECOVERED, exact, from the Milwaukee incident]**: get `metro_areas.timezone` right at creation
time even if `season_tag` is deferred — Milwaukee silently computed season/check-in boundaries on
Phoenix's clock for a period before this was caught and fixed. This is not optional cleanup; it is
a load-bearing platform column threaded through `apply_seasonal_active_on_tag_change()`,
`sync_seasonal_item_active()`, `season_days_until_start()`, and `prevent_expired_list_checkins()`.

**[RECOVERED]** Geography/list model to build against (fixed platform-wide since Denver, not
per-metro work): `metro_areas.is_active` gates public visibility everywhere (city selector,
`HomeScreen.jsx` GPS-nearest resolution, `lib/resolveDefaultMetro.js`) — build the whole
foundation with the metro inactive, verify, then flip `is_active=true` as the deliberate launch
trigger (M14). `items.city_id` is legacy/optional, not required. `curated_list_metros` gates
curated-list visibility (no rows = universal). Item-level `city_slug` overlay on
`curated_list_items`/`list_items` is nullable (NULL = universal).

## M1 — Geography / Neighborhood Map **[RECOVERED]**

Neighborhoods are one of the first things defined, before blind bulk item research — this
ordering is explicit in the Denver cycle and is now formalized as M1 preceding M2/M3.

Classify each area as `core_urban | important_neighborhood | suburb | destination_worthy_outer`,
and deliberately record areas that are excluded (a stated decision, not a silent omission).

**[RECOVERED, exact invariant]**: ring-2 radii must not overlap across the full neighborhood set,
verified **programmatically** (`verifyNoRingOverlap` in `metroLaunch.ts`), never eyeballed —
this held for all 20 Denver neighborhoods including the later Nederland/Eldora addition. Schema
default radii (20mi/40mi) are unsafe for a tightly-packed metro; tune per metro.

## M2 — Category Coverage Plan **[NEW — formalized; the underlying instinct is RECOVERED]**

Define per-category `minimumViable` and `healthyTarget` counts using CheckOff's existing
categories, plus category-specific quality notes (e.g. "must include at least one hidden/secret-
style experience"). **Never one arbitrary fixed count for every category** — Denver's real Sports
intake is direct evidence that categories need individually tuned targets, but no metro before
Denver had this as a stated plan going in; it was discovered reactively each time.

Proactively flag categories that were historically weak in prior metros (Shopping, Sports, Social,
Travel showed this pattern across multiple metros) for an M5 deep dive **before** M4 even runs, so
the loop below doesn't have to rediscover a known pattern from scratch every metro.

## M3 — Broad Discovery **[RECOVERED, informally practiced]**

Optimize for recall, local originality, and diversity — not a generic business directory. Research
iconic local things, hidden gems, hyperlocal favorites, quirky/participatory experiences, food/
drink specifics, unusual businesses, outdoor/sports/social/nightlife/arts/shopping/travel/family/
seasonal-tradition content. A first-pass candidate list is allowed to include stale/closed/
questionable candidates — verification (M6) happens later, deliberately not mixed into discovery.

`research_verifier` is the specialist that must run this — it is the only specialist trusted to
treat live external research as current-for-now evidence (see `capabilityRouting.ts`'s
`requiresLiveVerification`).

## M4 — Coverage Audit **[NEW as a named checkpoint; RECOVERED as a real gate]**

Count the real candidate pool by category and neighborhood/area. `auditCoverage()` in
`metroLaunch.ts` is the exact, pure implementation: flags `CATEGORY_BELOW_MINIMUM`,
`CATEGORY_BELOW_TARGET`, `GEOGRAPHIC_HOLE` (any `core_urban`/`important_neighborhood` with zero
items), and `CATEGORY_OVERREPRESENTED`.

This is a **required checkpoint** — a metro does not proceed to M6 verification with unresolved
`CATEGORY_BELOW_MINIMUM` or `GEOGRAPHIC_HOLE` gaps.

## M5 — Targeted Deep Dives **[RECOVERED, exact — this is the Denver Sports precedent]**

If a category is weak, `research_verifier` runs targeted research scoped to that category
specifically (e.g. "Shopping target 15, viable 6 → targeted Shopping research"). If a geographic
area is weak, targeted research scoped to that area (e.g. "North County underrepresented →
targeted Encinitas/Carlsbad/Oceanside/Vista research"). This is a loop, not a one-shot: research →
recount (return to M4) → detect remaining gaps → research again, until `deriveMetroLoopAction()`
returns `PROCEED_TO_VERIFICATION`. `metroLaunch.ts` formalizes the loop's decision point exactly;
this was previously an unnamed pattern that happened by necessity (Denver Sports), never a
declared, repeatable stage.

## M6 — Quality Verification **[RECOVERED]**

Attack the candidate list: closed businesses, discontinued products, stale menu items, outdated
experiences, wrong locations, duplicates, generic tourist filler, weak exact-item specificity,
wrong category/geography. Preserve the existing Google Places/location policy — coordinates come
from a live API call (`scripts/geocode-items.js` pattern), never estimated from memory.

## M6 → M5 Replacement Loop **[NEW — formalized; the need for it is RECOVERED]**

Every candidate removed during verification creates a deficit against the M2 plan. Recalculate the
category/geographic deficit it creates and route it back into M5 as a new targeted-research task —
loop until M4's gates pass again. `deriveMetroLoopAction` already models this generically: a
verification-caused deficit is not structurally different from a first-pass gap, it re-enters the
same M4↔M5 loop.

## M6.5 — CheckOff Editorial Pass **[NEW]**

Deliberately separate from discovery and verification (see `checkoff_editor/v1.md`). Discovery
finds truth; verification confirms truth; `checkoff_editor` then, and only then, writes the final
item wording. Do not let editorial voice creep into M3/M6 research notes.

## M7 — Catalog Construction **[RECOVERED]**

Build items/categories/neighborhoods/coordinates/metro relationships with `gen_random_uuid()`, not
invented UUIDs. **[RECOVERED, hard rule]**: new items do not automatically enter seasonal/themed
lists unless explicitly intended — this was a real, named product decision (the admin tool's
"Also add to active seasonal list(s)" checkbox exists specifically because this must be an
explicit per-item choice, not implicit).

## M8 — Curated Launch Experience **[RECOVERED]**

Permanent catalog, curated lists, audience-group content, launch seasonal/Official list where
applicable, hero/list imagery. `curated_lists.is_active=false` while staged — this actually hides
content now (the RLS double-policy gap that used to make it a no-op is fixed as of the Denver
cycle).

## M9 — Visual Coverage **[RECOVERED]**

Metro hero images, curated-list header images, and a metro-aware replacement for any hardcoded
onboarding content (Denver inherited a literal "Phoenix Fall 30" mock shown to every new user
regardless of metro — check whether this class of bug still needs a per-metro workaround).

## M10–M12 — Outreach Preparation / Execution / Response Operations **[RECOVERED]**

Reuse the existing Business Photo Outreach and Photo Moderation playbooks unchanged — identify
businesses/items for outreach, contact research, email/DM/contact-form, personalized confirmation
URL, confirmation/correction, photo submission, cling, follow-up. No new outreach mechanism per
metro.

## M13 — Launch Readiness **[RECOVERED]**

All 7 quality gates (`GEOGRAPHY`, `CATEGORY`, `QUALITY`, `CATALOG`, `LOCATION`, `PRESENTATION`,
`OUTREACH` — `evaluateMetroGates()`) must `PASS` or carry an explicit Jerry-approved exception.
Device QA: city selector, Home hero, Nearby/Discover ring-tiers, check-in boundary in local time,
no deep-link fallthrough to another metro, sane re-engagement behavior for a zero-activity account.

## M14 — Launch **[RECOVERED — always `APPROVAL_REQUIRED`]**

Flip `metro_areas.is_active=true`. This is the deliberate launch trigger, never a side effect of
any prior step, and Chief cannot perform it autonomously regardless of gate state
(`metro_launch.public_launch` is `APPROVAL_REQUIRED` in `standingAuthority.ts`, with no exception
path).

## M15 — Post-Launch **[NEW, lightweight]**

Confirm gate state remains true post-launch (no regression from a race with other work), hand
open outreach/response items to their owning playbook's normal WAITING/resume loop.

## Git-sync discipline **[RECOVERED, exact]**

Apply any time the worktree needs syncing, not metro-specific: stage explicitly (never
`git add -A`), check untracked files against `.gitignore` by content not just pattern-match, grep
the staged diff for key-shaped strings (`eyJ`, `AIza`, `sk-`, `service_role`,
`BEGIN PRIVATE KEY`, `Authorization: Bearer`, `api[_-]?key|secret|token|password`) before every
commit — this caught a real hardcoded Supabase anon key during the Denver cycle.
