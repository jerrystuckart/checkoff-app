## What actually happened, in one paragraph

Winston built Munich to 70 items across 10 neighborhoods, skewed hard toward Food & drink/Bar & drinks/Arts & Culture with generic actions, no secret mechanics, and difficulty locked at 1. Jerry ran that 70-item catalog through cleanup SQL that retired 21 stale/non-CheckOff-worthy originals, rewrote 9 more (body + category + tag corrections), and left 40 untouched. He then ran a separate, external Bulk Add Agent across (at least) five identifiable batches — wave1 (72 candidates, central Munich neighborhoods only), wave2 (39 items actually inserted, into 26 brand-new neighborhoods reaching well outside the city into surrounding municipalities like Erding, Freising, Aying, Andechs, Dachau, Starnberg), wave3 (17 candidates, including a second, differently-worded pass at two wave1 venues), and a final 6-row selective-fill batch — to expand and diversify the catalog. The live production catalog today has **184 active Munich items across exactly 36 neighborhoods (10 original + 26 new, confirming the "26 additional" claim exactly)**, still zero inactive items visible to this read-only role (consistent with the cleanup SQL's reversible soft-delete design), zero `is_secret` items, and difficulty still locked at 1 for all 184 rows — meaning the Bulk Add process fixed geography and category breadth dramatically but did **not** fix two of Winston's original structural failures (difficulty variance, secret mechanics), and it did not dedupe across its own waves (see the Kunst Oase / Vereinsheim case study in `02-new-item-contributions.md`).

## Still-unresolved, launch-blocking-if-ignored: difficulty and secret status

**Elevated to its own section per the extension pass's explicit instruction to keep this prominent, not buried in a table.** As of this update, **all 184 active Munich items still carry `difficulty = 1` and `is_secret = false` — no exceptions, unchanged since the original session and unchanged by the list rebuild.** `14-difficulty-and-secret-remediation-plan.md` now provides a full evidence-based rubric and a worked, item-level review queue (using real catalog items like Therme Erding, Café Frischhut, Maisinger Schlucht, Haus im Tal, and 'Boazn' at Ludwigsbrücke) — but it is a **plan only**, with **no executable remediation SQL**, and nothing in either the original analysis or this extension has changed either field in production. This remains the single most concrete, ready-to-scope piece of unfinished Munich work: the rubric exists, the review queue exists, and no code or data change has been made.

## The single most important calibration finding

**Difficulty and secret-mechanic variance were never touched by the Bulk Add process, and `M5_75_SEED_PORTFOLIO_AUDIT` does not fix them either** — they are structurally out of scope for a seed-stage audit (difficulty is an M6.5/editorial-time decision; secret-evidence *verification* depends on a `research_verifier` evidence contract that, per `seedPortfolioAudit.ts`'s own code comment, **does not yet populate any evidence fields today**, so every candidate defaults to `ownershipType: 'UNKNOWN_REQUIRES_VERIFICATION'` and `isSecretClaimed: undefined`). This means: even after M5_75 ships, a future metro run will reproduce Munich's exact zero-secret, difficulty-flatlined outcome unless (a) M6.5's CheckOff Editor is given explicit difficulty-variance guidance, and (b) the `research_verifier` evidence contract is actually extended to populate ownership/secret-evidence fields — both are still-open prerequisites, not yet implemented. If forced to pick the one fix that would have prevented the most Munich rework, it is **wiring a real `research_verifier` evidence contract before M5_75 can do anything with ownership/secret verification** — every other Munich failure (category imbalance, thin/absent geography, generic actions, cross-wave duplicates) is now caught by some combination of M2/M4/M5_75; this one is not caught anywhere yet.

## What could not be completed with real evidence

See `08-data-gaps-and-next-steps.md` for the full list. In short: (1) the live DB role's apparent RLS hiding of `is_active=false` rows meant the 21 retired original UUIDs could not be directly re-queried — their retired state rests on the cleanup SQL's own successful `COMMIT` and postflight assertion, not a fresh live read; (2) `public.categories` is not readable by this role, so category names were inferred from sample item bodies per `category_id` rather than read directly; (3) the 40 "implicitly untouched" original items were not individually re-diffed against a byte-for-byte original snapshot (the `NOT_APPLIED` patch files are a same-night draft, not a true pre-Bulk-Add snapshot); (4) source-key-to-domain mapping (Part 4) is inferred from co-occurring `source_urls` in the same CSV rows, not from an explicit legend file, because no such legend was provided.

**Confirmed: zero production writes occurred.** Every database interaction in this analysis (both the original session and the extension pass) was a `SELECT` query issued against `AGENT_SERVICE_DATABASE_URL`; no `INSERT`/`UPDATE`/`DELETE`/DDL was ever executed, and this role in fact lacks write intent by design (it also lacks `SELECT` on `public.categories`, confirming it is a constrained, non-privileged connection). The extension pass additionally had a real, already-executed 839-line list-rebuild transaction (`munich_lists_rebuild_no_temp_tables.sql`) available for read-only analysis and **never executed it** — it had already been `COMMIT`ed in production before the extension began, which is what made live verification against it possible in the first place.
