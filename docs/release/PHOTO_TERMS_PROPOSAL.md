## 1. Decisions applied
- Option B: the new license applies prospectively to photos submitted on or after the publication date using the updated consent screens. Existing users get an in app notice with the effective date, a summary, the Terms link and the removal route. Nothing says continued use or an existing `consent_ack` proves acceptance of the broader license.
- The old promise stays and is not narrowed to paid advertising: no use in advertising without separate explicit permission. The permitted "promote" language is limited to the app and our own website and pages.
- The correction that optional visit recovery stores precise location (Terms section 5) is kept.
- Retained photo visibility means the existing storage and access status. Deleted check in rows disappear from the app, so keeping a file does not mean it keeps being shown. Photos are never called private or confidential: check in photos open for anyone with the exact address, and partners can see photos on check ins for their items while the check in exists.
- Removal requests go to support@getcheckoff.com.

## 6. Consent evidence (applied in production 2026-10-09)
Schema: `check_ins.photo_terms_version`, `item_cover_candidates.consent_version`, `retained_checkin_photos.consent_version`, all nullable text, no default, no backfill, restricted by a format check to `photo-terms-v<n>`. The only pipeline change: `account_deletion_retain_inventory` includes the version and `account_deletion_process` copies it into `retained_checkin_photos`. Cover rows keep the column after anonymization. 20261009b also grants INSERT on the new `item_cover_candidates` column (that table uses column level grants; the first test found updated clients would otherwise get 42501).
Client rules: a version is written only when a photo is attached AND the consent line was shown on the submitting screen (standard check in, trip mode, visit confirmation, cover submission); mirror rows (fan out to other lists, list join credit) copy the source row's version and never invent one. Older clients send nothing, so their rows stay NULL; the publication date alone is not evidence. The value is client attested and the owner can edit their own rows through existing policies (limitation).
Test results (two disposable accounts, both deleted through the normal pipeline, fixtures then removed): updated client check in photo stored `photo-terms-v1`; old client payload (no field) accepted and stored NULL; free text rejected by the format check; updated cover submission stored `photo-terms-v1` after the grant fix, old cover payload NULL. After deletion: retained check in record kept `photo-terms-v1` (updated account) and NULL (old client), with columns only id, item, bucket, name, width, height, consent_version (no identity); retained cover rows unattributed, same status, not display eligible, not primary, not selected, versions preserved; files at neutral paths with no owner; auth, profile, check ins, badges, events, queue entries gone; anonymous completion counts +1 per account and then removed with the fixtures (table back to its 2 cells). The deletion took about 2.5 minutes (one retry of the storage step), within the normal retry design.
Not integration tested (unit and source level only): fan out mirror rows and list join credit copies.
