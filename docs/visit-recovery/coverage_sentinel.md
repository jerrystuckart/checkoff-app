## Problem
iOS allows 20 monitored regions per app. The tracker registers the nearest 19 eligible venues at launch/foreground and never updates them while backgrounded. Walking through a dense town leaves the covered set (nearest-19 radius: Florence ~350 m, Positano ~1.4 km).

## Design
* **Budget:** 18 venues + 1 sentinel = 19 registered, 1 spare (`regionBudget.js`). A test scans the source and fails if any other file registers regions.
* **Sentinel:** one circle centred on the position where the set was chosen, exit-only in intent. Radius comes from real coverage (`sentinel.js`): `distance to the nearest eligible-but-unwatched venue − that venue's circle − 60 m`, clamped to 150–1500 m. While the phone is still inside the sentinel, no unwatched venue's circle can have been entered. In very dense areas the bound falls below what iOS can honor, so the minimum is used and the refresh row reports `tight: true` (short gaps are possible there and are reported, not hidden).
* **Refresh:** when iOS reports the sentinel exit (relaunching a system-terminated app in the background), the geofence task verifies with a fresh fix (at most 2 minutes old), then re-chooses the 18 nearest eligible venues around the new position with the *same* eligibility rule and ordering as the classic path, and re-registers them plus a new sentinel. No continuous GPS.
* **Cache:** catalog rows within 60 km of the last fetch are stored on the device (`coverageCache.js`), so a refresh needs no network while the phone stays within 30 km of the cache centre. Older than 3 days: refetched when online, still used (flagged `stale`) offline. Older than 30 days, or beyond the cached area, or empty: **not** used to choose a set. The registered set is kept, the attempt is logged as `kept_previous_set`, `needsRefresh` is set, and the next geofence event or app open retries.
* **Never touches visits:** `eventRouter.js` decides first; the sentinel id can only produce `sentinel_*` actions, so it cannot reach the presence RPCs, candidate creation, check-offs or points (property-tested; the sentinel code block is also asserted not to reference those functions).
* **Flapping and overlap:** a sentinel is re-centred on the fresh fix so the phone starts at its centre; exits that a fresh fix contradicts (within 70% of the radius) are ignored; at least 60 s between sentinel refreshes and at most 40 per hour; refreshes are single-flight with coalescing (`refreshCoordinator.js`); an unchanged set is not re-registered on foreground; an exit within 20 s of our own registration ("born outside") re-centres at most twice.
* **Presence sessions:** a refresh never edits the open-session map. Venues with an open session are placed first in selection so their exit is still delivered. Removing regions raises no exit; the exits iOS delivers as state determinations right after any registration are recognised by the existing registration-window rule and reconciled **without** a departure time.
* **Already inside a venue when it is registered:** iOS determines state and delivers *enter*; the phone reports it and the **server** stamps `entered_at` with its own clock (verified in a rolled-back DB check), so time before the report is never counted and a re-delivered enter keeps the original stamp.
* **Opt-out:** turning visit recovery off clears every device key (`trackerKeys.js`), bumps an epoch that cancels an in-flight refresh, and a late sentinel callback with no sentinel state does nothing.
* **Public users:** run the unchanged classic refresh. `refreshGeofences` is byte-for-byte the old function; the geofence task now routes through `eventRouter` for venue events too, with the same decisions (covered by the pre-existing presence tests plus the harness).

## Diagnostics
`geofence_registration_log` gains `refresh_cause` (`app_start|foreground|opt_in_change|manual|sentinel_exit|sentinel_retry|sentinel_born_outside`) and `coverage` (venues, eligibleNearby, farthestVenueM, nextUnmonitoredM, sentinelRadiusM, tight, openPreserved, cacheStatus/Source/AgeMs, profileSource, fixAccuracyM, durationMs, or a `reason` when the set was kept), and a `kept_previous_set` state. `geofence_debug_events` accepts `sentinel_exit`, `sentinel_ignored`, `sentinel_born_outside`. Diagnostics that cannot be uploaded offline are queued on the device and sent with the next refresh. The tester debug panel shows the last cause, sentinel radius, distance to the next unwatched venue and cache source. `scripts/visit-field-test-report.mjs` turns a day's rows into stage verdicts.

## What is tested, and what cannot be
Tested (`sentinelCoverage.test.js`, `sentinelTracker.harness.test.js`): region budget; radius from density (Positano vs Florence vs a packed block); the real eligibility rule; classic/sentinel selection equivalence; open-venue preservation; event routing; exit verification; rate gate; cache validity and offline decisions; single-flight concurrency; opt-out; flag gating; and the **real tracker module** (bundled, with only React Native/expo/Supabase faked) driven through its task callback: sentinel exit, ignored exit, enter, five concurrent exits, offline cache refresh, offline with no cache (kept + queued log + retry), stale fix, opt-out, born-outside, preserved presence, venue path, reconcile-without-departure, classic path for non-flag users. Backend, rolled back: new columns/states/event types under RLS as the real tester, server-stamped entry, reconcile without credit (`supabase/checks/`).

Cannot be tested off-device: that iOS relaunches the terminated app for the sentinel exit on this phone, the real exit lag/hysteresis, whether re-registering from inside the task callback behaves on device, battery over a day, and that detection follows. Apple's documented behaviour supports the design; this build makes no claim beyond that.

## Known limits
* **Force-quit:** iOS does not relaunch a force-quit app for region events until it is opened again. Nothing in JS can change that.
* expo-location's JS option is `notifyOnEnter` but the iOS consumer reads `notifyOnEntry`, so the option is ignored (both enter and exit are delivered). The router ignores sentinel enters, so nothing depends on it.
* Dense old-town areas: the sentinel may be as small as 150 m (reported as `tight`), giving frequent refreshes; the 60 s gap and 40/hour ceiling bound the battery cost.
* Requires "Always" location; relies on iOS region monitoring, which is coarse (tens of metres of hysteresis, delivery lag).
* **If the field test shows relaunch or in-task re-registration is unreliable:** the supported alternative is the OS *significant-location-change* service (`CLLocationManager.startMonitoringSignificantLocationChanges`), which expo-location only exposes bundled with continuous updates. A small native module exposing it alone would need a new binary (and therefore a new runtime); do not publish that to `81dbd1f1…`.
